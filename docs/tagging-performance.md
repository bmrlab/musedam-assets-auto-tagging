# 标签处理性能与软删除

核对日期：2026-11-06。自动打标分支 `codex/tagging-performance-soft-delete` 基于 `b3a8e47`（`local/test-master` / `test/master`）；主站 Java 分支 `codex/tagging-performance` 基于 `cc955a2007`（本地 `origin/master`）。两者都未合入、推送或部署，没有合并元数据功能分支。打标远端最新 HEAD 的 `ls-remote` 因 git.tezign.com TLS 握手失败未能回查，以上打标基线按已有 tracking ref 核对。

## 请求链路与瓶颈

- 标签管理的批量创建已经走 `/api/muse/import-tag-tree`，按层批量保存并持久化远端回执。本次保留此路径；不退回逐条 `merge-tags`。
- 特征库表格导入缺失标签时，原来按每条路径重复查共享父节点，并逐行插入。现在团队范围读取一次、按层去重，每批最多 500 行 `createManyAndReturn`，整个本地补建使用团队事务锁。
- 删除入口原来对全团队数组反复 `filter` / `find` 构造子树及祖先上下文，复杂度随节点数平方增长；现在构建父子、ID 索引。远端只提交一个目标节点的删除操作及必要祖先上下文，由主站同一事务递归处理整棵子树，不逐个提交后代节点。
- 主站 `merge-tags` 原来每个操作都扫描 `tagTreeMap.values()` 找 ID，且全树加载用带 COUNT 的 OFFSET 分页。现在 ID 与同级名称分别建请求内索引，改名或移动时释放旧名称索引；加载改用 `id > cursor ORDER BY id LIMIT 500`，保留组织、类型及 MyBatis 逻辑删除过滤。
- 自动打标队列按全局 `status=pending`、`createdAt` 取候选。原 `(teamId,status)` 索引导致读取全部待处理项后排序；新增仅覆盖 pending 行的 `(createdAt,id) INCLUDE(taskType)` 索引。现有并发槽位、测试保留槽和候选池大小保持原值。
- 标签同步原来使用模块全局 Map，两个团队并发会清空彼此的映射；现在 Map 仅属于当前同步请求。

索引不是所有耗时的原因。已有开发库只有 14,797 个标签，没有队列或审核历史，不能从它计算真实素材打标的模型阶段耗时。队列现有阶段计时及并发机制继续保留，不据此放宽模型并发或改变预测质量。

## 已入队却迟迟不开始

`TaggingQueueItem_pending_createdAt_idx` 优化领取待处理任务的 SQL，不代表任务能立即获得执行槽位。该索引目前只在本地独立测试库应用；未部署到用户当前使用的实例。没有新增发起任务的其他索引，也没有据此改变去重、授权或扣点规则。

源码存在可复现的整批等待：`processPendingQueueItems` 会等待同批所有任务结束，内嵌调度器和外部调度脚本又等待该调用返回。即使某些任务已完成并释放槽位，仍可能被同批的长任务阻止进入下一轮；worker 模式下 web 入队 kick 不会处理队列，尤其容易暴露这一缺口。

现在每个任务成功、失败或超时结束后，都会通过已有的 2 秒节流立即请求补领。只串行化数据库候选选择和派发阶段，不串行化模型执行；派发期间收到的新补领请求会保留到派发完成后执行。并发预留按已经在执行的任务计算，防止多轮补领挤占标签树槽位或让测试任务持续抢走正式任务的槽位。默认总并发及素材打标上限保持原配置。

回归测试直接调用实际的队列消费入口，用受控任务复现“一个慢任务仍在运行、同批快任务已完成、第三条仍在等待”的场景。关闭完成后补领时，第三条不能开始；启用后，在慢任务未完成时就能补领第三条。还覆盖失败后的补领、重叠调度不重复启动、预留槽跨批次计数。6 个相关文件共 45 项通过，类型检查和修改文件 lint 通过。这是本地调度行为验证，没有任务 ID 或当前实例日志，不能断言用户环境的长时间排队已被定位或修复。

领取日志 `Queue item claimed` 新增 `waitMs`、各车道活动任务数；`all slots busy` 日志也包含各车道活动数。部署后可结合这些日志区分已经领取但执行慢、所有槽位占满、worker 没有领取任务等情况。worker 是否启动/反复退出、QUEUE_PAUSED 状态和上游模型耗时仍需当前实例运行证据。

## 软删除语义

主站 `TagEntity` 继承 `CommonBaseEntity`，通过 `@TableLogic status` 已软删除；主站素材、文件夹、可见性等当前关联沿用原有删除规则。本地 `AssetTag` 新增 `deletedAt`，不清空历史 FK，不改变原名称、slug、parentId、extra。递归 CTE 在团队范围更新整棵子树；覆盖导入及主站对齐中的过期标签同样软删除。

正常标签树、数量、编辑、特征推荐和最终主站打标解析只接受 `deletedAt IS NULL`。历史审核和任务仍保留原 ID 与路径；历史统计仍按审核/任务本身计数。特征库当前展示隐藏已删除标签，其底层历史关联不被删除。团队迁移导出仍包含墓碑记录。

未删除记录用两个部分唯一索引分别约束根节点、同父同名子节点；删除记录不占用活动名称。同名重建或重新导入创建新 ID，不复用旧审核关联。主站返回含已删除 slug 的旧快照/旧回执时拒绝保存；取消的回执不允许迟到网络响应改回可恢复状态。删除以及覆盖导入作废相关未完成回执，用户主动再次提交时使用新请求号。

语句级数据库触发器在标签 INSERT/UPDATE/DELETE 的同一事务内，每个团队更新一次 `tagging-config-version`。因此旧缓存最多用于已经开始的任务；最终主站回写前再次查询活动标签，不能用已删除的旧 ID 恢复标签。事务回滚同时回滚版本。所有已改本地树结构写入沿用同一个团队 advisory lock，不跨网络持有数据库事务；独立删除入口与导入还共用团队导入租约。

## 本地测量

测试使用 `127.0.0.1:55439` 的专用 `tag_import_test_*` 数据库。性能测试会清空指定测试库的 Team 及其关联表，绝不能指向业务库。所有远端调用在这些测试中使用受控替身；请求数是实际批处理函数发送给替身的次数。耗时是本机单次测量，不代表生产端到端 SLA。

| 场景 | 优化前 | 优化后 |
| --- | --- | --- |
| 1,000 条四级路径，1,610 个不同节点 | 7947.3 ms，5610 次 SQL | 174.3 ms，9 次 SQL |
| 200,000 个任务，1% pending，取 200 个正式任务 | 3.119 ms | 0.203 ms |
| 1,001 个标签及 1,000 个审核关联，本地删除 | 252.3 ms，物理删除 | 14.3 ms，保留关联软删除 |
| 20,000 节点子树规划 | 2584.0 ms | 5.9 ms |
| 20,000 节点子树删除请求 | 40 次 | 1 次 |
| 主站 20,000 标签逐项 ID 查找（含新版索引构建） | 2,133.4 ms | 25.3 ms |

队列计划从 Bitmap Heap Scan + top-N Sort 改为 pending 索引的 Index Scan；共享缓冲块命中从 2,158 降至 302。旧版创建循环与新版使用相同数据和同一已迁移数据库。物理删除基线在事务中回滚，软删除基线也回滚，以比较同一组 FK 数据。

## 多商品覆盖与名称规格规则（2026-11-06）

## 2026-11-11：大标签树请求与图片原生内存
